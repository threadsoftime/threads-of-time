## 1. Episode Schema

Episodes are the primary memory unit. One episode = one discrete event the bot experienced, observed, or reflected on. The schema is append-mostly (R1 requires delete/update, so it is not append-only).

### 1.1 DDL

```sql
-- SPDX-License-Identifier: GPL-2.0-or-later
-- Migration: 001_episodes.sql

CREATE TABLE episodes (
    episode_id          INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp           INTEGER NOT NULL,          -- unix epoch ms (event time, NOT write time)
    created_at          INTEGER NOT NULL            -- unix epoch ms (row write time)
                        DEFAULT (unixepoch('now') * 1000),
    content_text        TEXT    NOT NULL            -- the memory text; max ~4000 chars (seq-len limit)
                        CHECK  (length(content_text) > 0 AND length(content_text) <= 4000),
    content_embedding_id INTEGER,                   -- rowid in embeddings_vec; NULL until embedded
    episode_type        TEXT    NOT NULL            -- see §1.2 for valid values
                        CHECK  (episode_type IN (
                            'chat',        -- player/bot said something to the bot
                            'combat',      -- notable combat event (kill, near-death, group wipe)
                            'social',      -- non-combat interaction with a player or NPC
                            'quest',       -- quest accept/complete/fail/objective
                            'discovery',   -- new place, item, mechanic discovered
                            'goal',        -- goal proposed, adopted, completed, or abandoned
                            'reflection',  -- bot-generated synthesis: distilled from other episodes
                            'observation'  -- passive observation (player joined, someone died nearby)
                        )),
    salience_score      REAL    NOT NULL DEFAULT 0.5
                        CHECK  (salience_score >= 0.0 AND salience_score <= 1.0),
    last_recalled_at    INTEGER,                    -- unix epoch ms; NULL = never recalled
    recall_count        INTEGER NOT NULL DEFAULT 0
                        CHECK  (recall_count >= 0),
    source              TEXT    NOT NULL DEFAULT 'self'
                        CHECK  (source IN ('self', 'chat', 'observed', 'system')),
    metadata            TEXT                        -- JSON blob; arbitrary per-episode-type fields
);

-- Primary access patterns: bot's episodes by recency, by type
CREATE INDEX ix_episodes_timestamp        ON episodes(timestamp DESC);
CREATE INDEX ix_episodes_episode_type     ON episodes(episode_type, timestamp DESC);
CREATE INDEX ix_episodes_salience         ON episodes(salience_score DESC);
CREATE INDEX ix_episodes_last_recalled    ON episodes(last_recalled_at DESC);
CREATE INDEX ix_episodes_embedding        ON episodes(content_embedding_id)
    WHERE content_embedding_id IS NOT NULL;
```

### 1.2 Episode type vocabulary

| type | description |
|---|---|
| `chat` | A message a player or NPC said TO this bot in say/party/whisper |
| `combat` | Kill, near-death (HP < 15%), group wipe, first kill on a boss |
| `social` | Greeting, grouping, trade, emote, party invite — non-combat human interaction |
| `quest` | Quest events: accept, objective met, complete, fail, handover |
| `discovery` | First visit to a map zone, first loot of an item class, new mechanic observed |
| `goal` | Goal proposed by a player, adopted by the bot, completed, or abandoned |
| `reflection` | Bot-generated summary distilled from multiple prior episodes |
| `observation` | Passive observations: player went offline, someone died, weather changed |

Rationale for typed episodes: time-decay half-lives differ by type (§7). Retrieval can filter by episode_type for targeted recall ("what did Alice tell me?" = type=chat + entity=Alice).

### 1.3 `metadata` field structure (per type)

JSON blob; parseable but not schema-enforced in SQLite. Convention:

- `chat`: `{"speaker_name": "Alice", "channel": "party", "raw_text": "..."}`
- `combat`: `{"enemy_name": "Hogger", "outcome": "kill|wipe|near_death", "hp_pct_at_event": 12}`
- `quest`: `{"quest_id": 123, "quest_name": "...", "event": "complete"}`
- `discovery`: `{"zone_name": "Westfall", "item_id": 1234}`
- `goal`: `{"goal_description": "...", "source_player_guid": 1234567}`
- `reflection`: `{"source_episode_ids": [1, 5, 12]}`

## 2. Entity Schema

Entities are persistent records of known players, NPCs, items, locations, and factions. The M:N join table links entities to the episodes they appear in.

### 2.1 DDL

```sql
-- SPDX-License-Identifier: GPL-2.0-or-later
-- Migration: 002_entities.sql

CREATE TABLE entities (
    entity_id       INTEGER PRIMARY KEY AUTOINCREMENT,
    entity_kind     TEXT    NOT NULL
                    CHECK  (entity_kind IN (
                        'player',    -- human-controlled character (has game GUID)
                        'npc',       -- non-player character (has game GUID / name)
                        'item',      -- item template (has item_entry_id)
                        'location',  -- map zone or named place (has map_id + zone_id)
                        'faction'    -- in-game faction (has faction_id)
                    )),
    entity_key      TEXT    NOT NULL,  -- canonical key: low-GUID for player/npc, entry for item,
                                       -- "mapId:zoneId" for location, faction_id for faction
    display_name    TEXT    NOT NULL,  -- human-readable label
    summary         TEXT,              -- agent-maintained running summary (updated by PATCH)
    first_seen_at   INTEGER NOT NULL   -- unix epoch ms
                    DEFAULT (unixepoch('now') * 1000),
    last_seen_at    INTEGER,           -- unix epoch ms; updated on each episode link
    total_episodes  INTEGER NOT NULL DEFAULT 0,  -- denormalized count; updated on insert/delete
    metadata        TEXT,              -- JSON; e.g., {"class": "warrior", "level": 20}
    UNIQUE (entity_kind, entity_key)
);

CREATE INDEX ix_entities_kind_key        ON entities(entity_kind, entity_key);
CREATE INDEX ix_entities_display_name    ON entities(display_name);
CREATE INDEX ix_entities_last_seen       ON entities(last_seen_at DESC);

-- M:N join: which entities appear in which episodes
CREATE TABLE episode_entities (
    episode_id  INTEGER NOT NULL REFERENCES episodes(episode_id) ON DELETE CASCADE,
    entity_id   INTEGER NOT NULL REFERENCES entities(entity_id)  ON DELETE CASCADE,
    role        TEXT    NOT NULL DEFAULT 'participant'
                CHECK  (role IN (
                    'subject',      -- the entity the episode is primarily about
                    'participant',  -- present but not the main subject
                    'target',       -- entity on the receiving end of an action
                    'witness'       -- observed but not interacted with
                )),
    PRIMARY KEY (episode_id, entity_id, role)
);

CREATE INDEX ix_ee_episode    ON episode_entities(episode_id);
CREATE INDEX ix_ee_entity     ON episode_entities(entity_id);
CREATE INDEX ix_ee_entity_role ON episode_entities(entity_id, role);
```

### 2.2 Entity resolution on write

When writing an episode with entity references, the write route:

1. Looks up `(entity_kind, entity_key)` in `entities`; if found, updates `last_seen_at`.
2. If not found, inserts a new entity row with the provided `display_name`.
3. Inserts `episode_entities` rows.
4. Updates `entities.total_episodes` via a trigger (see §2.3).

### 2.3 Trigger to maintain `total_episodes`

```sql
-- part of 002_entities.sql
CREATE TRIGGER ee_ai AFTER INSERT ON episode_entities BEGIN
    UPDATE entities SET total_episodes = total_episodes + 1
    WHERE entity_id = NEW.entity_id;
END;

CREATE TRIGGER ee_ad AFTER DELETE ON episode_entities BEGIN
    UPDATE entities SET total_episodes = MAX(0, total_episodes - 1)
    WHERE entity_id = OLD.entity_id;
END;
```

## 3. sqlite-vec Virtual Table

Dense vectors are stored in a sqlite-vec `vec0` virtual table. The rowid of each row in `embeddings_vec` matches the `episode_id` in `episodes` — this convention (identical to Munin's `vec_embeddings` pattern) keeps the join trivial.

### 3.1 DDL

```sql
-- SPDX-License-Identifier: GPL-2.0-or-later
-- Migration: 003_embeddings_vec.sql

-- Dense vector store via sqlite-vec.
-- Dimension MUST match EMBEDDING_DIM in tot_memory/db/schema.py.
-- For nomic-embed-text: 768 (see §4 for model selection rationale).

CREATE VIRTUAL TABLE embeddings_vec USING vec0(
    embedding float[768]
);
```

`rowid` in `embeddings_vec` = `episode_id` in `episodes`. On episode insert, the write route inserts `(episode_id, embedding_bytes)` into `embeddings_vec` and sets `episodes.content_embedding_id = episode_id`.

### 3.2 Python constant

```python
# tot/memory/src/tot_memory/db/schema.py
# SPDX-License-Identifier: GPL-2.0-or-later

EMBEDDING_DIM: int = 768  # nomic-embed-text; change here AND in 003_embeddings_vec.sql together
```

This constant is the single source of truth. The embedding client (§5) validates the returned vector length against it.

## 4. Recommended BYOLLM Embedding Model

### 4.1 Recommendation

**Use `nomic-embed-text` at 768 dimensions.**

This is the model the ToT parent spec (§4.5, §6.3, §6.4) uses as the default example for the dev stack and the operator `.env`. It is already documented in the `BRAIN_EMBEDDINGS_MODEL=nomic-embed-text` env var example. It is available on Ollama (the cheapest operator path), OpenAI-compatible, and returns 768-dimensional L2-normalized vectors.

| Property | Value |
|---|---|
| Model string (exact) | `nomic-embed-text` |
| Provider | Any OpenAI-compatible `/v1/embeddings` endpoint; Ollama ships it out of the box |
| Embedding dimension | **768** |
| Max input tokens | 8192 (Ollama nomic-embed-text v1.5 default context) |
| Normalization | L2-normalized output; safe to use raw cosine similarity (dot product of normalized = cosine) |
| Cost | Free on local Ollama; ~$0.0001/1K tokens on commercial APIs |

### 4.2 Sequence-length constraint on content_text

The `episodes.content_text` column has a 4000-character CHECK constraint (§1.1). At ~4 chars/token this yields ~1000 tokens — safely within nomic's 8192-token context window. Episode text should be written as a single coherent sentence or short paragraph (50–300 chars ideal; 4000 chars maximum). The brain must truncate at write time if a content string would exceed 4000 chars.

### 4.3 Why not `all-MiniLM-L6-v2` (384-dim)?

`all-MiniLM-L6-v2` is the system prompt's stated default and is lighter. However:

- The parent spec's `.env.example` and dev-stack docs explicitly name `nomic-embed-text`.
- nomic-embed-text has materially better English semantic recall at the cost of 2× the storage (768 vs 384 floats per episode = 3 KB vs 1.5 KB per episode at full precision). At 100K episodes per bot × 15 bots = 1.5M rows, the delta is ~2.2 GB vs 1.1 GB — both comfortably fit on any NVMe.
- The consistency between the spec's env-var docs and the chosen model matters for operators configuring their setup.

If an operator wants to use `all-MiniLM-L6-v2`, they must change `BRAIN_EMBEDDINGS_MODEL` AND rebuild the DB from scratch (or run the backfill procedure in §5.4) because the dimension is baked into the sqlite-vec DDL. Document this prominently in `docs/byollm-setup.md`.

### 4.4 API contract ToT expects

```
POST {BRAIN_EMBEDDINGS_URL}/embeddings
Content-Type: application/json
Authorization: Bearer {BRAIN_EMBEDDINGS_API_KEY}   (omitted if key is empty string)

{
  "model": "{BRAIN_EMBEDDINGS_MODEL}",
  "input": "text to embed"
}

→ 200 OK
{
  "data": [
    { "embedding": [0.123, ...], "index": 0 }
  ],
  "model": "nomic-embed-text"
}
```

The client checks `len(data[0]["embedding"]) == EMBEDDING_DIM` and raises `ValueError` on mismatch. This catches operators who configure `BRAIN_EMBEDDINGS_MODEL=nomic-embed-text` but accidentally point `BRAIN_EMBEDDINGS_URL` at an endpoint serving a different model.

## 5. Embedding Pipeline

### 5.1 Decision: synchronous write path

The write path generates the embedding synchronously before returning HTTP 201. The alternative (async background queue) adds complexity (queue persistence, failure retry, eventual consistency) that is not warranted at 1.0.0 scale.

Throughput calculation: with `TOT_LIVING_BOT_COUNT=10` and one episode write per notable event (expected ~1-3 per minute per bot), the peak load is ~30 writes/minute = 0.5 writes/second. Each embedding call is ~20-80ms on local Ollama (CPU). At 0.5 writes/second this is trivially below saturation.

Latency budget for a `memory.write` call: 5ms (FastAPI overhead) + 50ms (embedding call) + 5ms (SQLite insert) = ~60ms. R2 specifies sub-100ms p95 for search; writes have no stated p95 but 60ms is acceptable.

If embedding is unavailable (network timeout, endpoint down), the write route writes the episode row with `content_embedding_id = NULL` and returns HTTP 201 with `"embedding_generated": false`. The episode is still readable and BM25-searchable; it just won't appear in dense-vector results until backfilled.

### 5.2 Write-path pseudocode

```python
async def write_episode(bot_guid: str, body: WriteEpisodeRequest) -> WriteEpisodeResponse:
    conn = open_bot_db(settings.data_dir, bot_guid)
    run_migrations(conn)

    # Step 1: Try to embed synchronously
    embedding_generated = False
    vec: list[float] | None = None
    try:
        vec = await embeddings_client.embed(body.content_text)
        embedding_generated = True
    except Exception as exc:
        logger.warning("Embedding call failed for bot %s: %s — episode will be written without embedding", bot_guid, exc)

    # Step 2: Insert episode row
    episode_id = insert_episode(conn, body)

    # Step 3: If embedding succeeded, insert into vec table
    if vec is not None:
        insert_embedding(conn, episode_id, vec)
        conn.execute("UPDATE episodes SET content_embedding_id = ? WHERE episode_id = ?", (episode_id, episode_id))

    # Step 4: Upsert entities + episode_entities
    upsert_entities(conn, episode_id, body.entities)

    conn.commit()
    return WriteEpisodeResponse(episode_id=episode_id, embedding_generated=embedding_generated)
```

### 5.3 L2 normalization requirement

`nomic-embed-text` returns L2-normalized vectors by default. No additional normalization step is needed. If the operator substitutes a different model, the embedding client MUST normalize before storing:

```python
import math

def l2_normalize(vec: list[float]) -> list[float]:
    norm = math.sqrt(sum(x * x for x in vec))
    if norm < 1e-12:
        return vec
    return [x / norm for x in vec]
```

The current plan assumes nomic-embed-text and skips explicit normalization. A comment in `embeddings/client.py` documents this assumption.

### 5.4 Backfill strategy for un-embedded episodes

Un-embedded episodes (written when the embedding endpoint was down) are those with `content_embedding_id IS NULL`. The backfill tool is `tot-memory-backfill` (a CLI entry point in `tot/memory/src/tot_memory/__main__.py`):

```
BRAIN_EMBEDDINGS_URL=http://... BRAIN_EMBEDDINGS_MODEL=nomic-embed-text \
    python -m tot_memory backfill --data-dir data/memory/ --bot-guid <guid> [--all-bots]
```

It iterates `SELECT episode_id, content_text FROM episodes WHERE content_embedding_id IS NULL ORDER BY created_at ASC`, embeds each row, updates `embeddings_vec` + `episodes.content_embedding_id`. Idempotent; safe to run while the sidecar is running (WAL mode handles concurrent reads).

Progress logged as JSONL to stderr: `{"bot_guid": "...", "backfilled": 120, "remaining": 0, "elapsed_s": 4.2}`.

## 6. Hybrid Retrieval Algorithm

### 6.1 Two-stage design

**Stage 1: Candidate generation.** Run FTS5 (BM25) and sqlite-vec (dense KNN) independently, each over-fetching (top-N = max(50, top_k * 10)). Union the results and deduplicate by `episode_id` (keep higher score per source). This gives a candidate set of up to 100 episodes for a `top_k=5` query.

**Stage 2: Hybrid scoring.** Score each candidate with the formula below. Apply entity filter as a hard filter (episodes without ANY of the required entity IDs are excluded before scoring). Sort descending. Apply MMR diversity reranking (§6.3). Return top-K.

### 6.2 Scoring formula

```
hybrid_score(episode, query) =
    (α · bm25_norm(episode, query) + β · dense_sim(episode, query))
  · decay(episode.timestamp)
  · (1.0 + γ · episode.salience_score)
  + δ · entity_match_score(episode, query.entity_ids)
```

Where:

| Symbol | Default | Description |
|---|---|---|
| `α` | 0.45 | BM25 weight |
| `β` | 0.45 | Dense cosine similarity weight |
| `γ` | 0.20 | Salience boost multiplier (multiplies the decay·blend, additive in terms of salience) |
| `δ` | 0.15 | Entity match bonus per matched entity |
| `decay(t)` | see §7 | Time-decay multiplier in [0.0, 1.0] |

All weights are runtime-configurable via env var: `MEMORY_SCORE_ALPHA`, `MEMORY_SCORE_BETA`, `MEMORY_SCORE_GAMMA`, `MEMORY_SCORE_DELTA`. Default values shown above. Documented in `tot/memory/src/tot_memory/config.py`.

**`bm25_norm`**: SQLite FTS5 returns a negative rank (more negative = better). Normalize to [0, 1]:
```python
def bm25_norm(rank: float, scale: float = 5.0) -> float:
    """Convert FTS5 negative rank to [0, 1]. rank is in [-∞, 0]."""
    return 1.0 / (1.0 + math.exp(rank / scale))   # sigmoid; rank=0 → 0.5; rank=-5 → ~0.73
```

**`dense_sim`**: sqlite-vec returns L2 distance. Convert to similarity:
```python
def distance_to_sim(distance: float) -> float:
    """L2 distance → cosine similarity proxy. For L2-normalized vectors: cos_sim = 1 - (d²/2)."""
    return max(0.0, 1.0 - (distance ** 2) / 2.0)
```

**`entity_match_score`**: For each entity ID in `query.entity_ids` that appears in `episode_entities` for this episode, add `δ`. Capped at `3 * δ` (diminishing returns beyond 3 entity hits).

### 6.3 MMR diversity reranking

Maximum Marginal Relevance prevents returning N identical episodes. After scoring, select top-K with MMR:

```python
def mmr_rerank(candidates: list[ScoredEpisode], embeddings: dict[int, list[float]],
               top_k: int, lambda_: float = 0.7) -> list[ScoredEpisode]:
    selected: list[ScoredEpisode] = []
    remaining = list(candidates)

    while len(selected) < top_k and remaining:
        if not selected:
            # First pick: highest hybrid score
            best = max(remaining, key=lambda e: e.score)
        else:
            # MMR: balance relevance vs. redundancy
            selected_embs = [embeddings[e.episode_id] for e in selected
                             if e.episode_id in embeddings]
            best = max(remaining, key=lambda e: (
                lambda_ * e.score
                - (1.0 - lambda_) * max_cos_sim(embeddings.get(e.episode_id, []), selected_embs)
            ))
        selected.append(best)
        remaining.remove(best)

    return selected
```

`lambda_ = 0.7` weights relevance more than diversity. Configurable via `MEMORY_MMR_LAMBDA` env var.

### 6.4 Worked example

**Query:** "What did Alice tell me about the AH?"
**entity_ids:** [alice_entity_id]
**top_k:** 3

Suppose the FTS5 top-3 candidates from `episodes_fts MATCH 'Alice OR AH OR "auction house"'`:
- Episode 42: bm25_rank=-1.2 → bm25_norm=0.595; dense_sim=0.81; timestamp 2h ago (decay=0.943); salience=0.8; entity_match=1 (Alice present)
- Episode 17: bm25_rank=-2.5 → bm25_norm=0.549; dense_sim=0.71; timestamp 3d ago (decay=0.485); salience=0.5; entity_match=1
- Episode 8:  bm25_rank=-0.8 → bm25_norm=0.581; dense_sim=0.73; timestamp 5min ago (decay=0.999); salience=0.3; entity_match=0

Using defaults (α=0.45, β=0.45, γ=0.20, δ=0.15):

- Episode 42: (0.45×0.595 + 0.45×0.81) × 0.943 × (1 + 0.20×0.8) + 0.15×1 = (0.268 + 0.365) × 0.943 × 1.16 + 0.15 = 0.633 × 0.943 × 1.16 + 0.15 = 0.692 + 0.15 = **0.842**
- Episode 17: (0.45×0.549 + 0.45×0.71) × 0.485 × (1 + 0.20×0.5) + 0.15×1 = (0.247 + 0.320) × 0.485 × 1.10 + 0.15 = 0.567 × 0.485 × 1.10 + 0.15 = 0.302 + 0.15 = **0.452**
- Episode 8:  (0.45×0.581 + 0.45×0.73) × 0.999 × (1 + 0.20×0.3) + 0.15×0 = (0.261 + 0.329) × 0.999 × 1.06 = 0.590 × 0.999 × 1.06 = **0.625**

Ranked order before MMR: 42 (0.842), 8 (0.625), 17 (0.452). MMR then checks if episode 8's embedding is close to episode 42's — if they're near-duplicates, episode 17 might be preferred despite its lower score.

## 7. Time-Decay Function

### 7.1 Function

```python
import math

def decay(timestamp_ms: int, now_ms: int, half_life_s: float) -> float:
    """Exponential decay: 1.0 when fresh, 0.5 at half_life_s, approaches 0.0 asymptotically.

    Uses formula: exp(-ln(2) * Δt_s / half_life_s).
    Clipped to [DECAY_FLOOR, 1.0].

    Args:
        timestamp_ms: episode.timestamp in epoch milliseconds (the EVENT time, not write time)
        now_ms:       current epoch milliseconds
        half_life_s:  half-life in seconds; episode worth 50% of fresh at this age
    """
    delta_s = max(0.0, (now_ms - timestamp_ms) / 1000.0)
    raw = math.exp(-math.log(2.0) * delta_s / half_life_s)
    return max(DECAY_FLOOR, raw)

DECAY_FLOOR: float = 0.05   # Configurable via MEMORY_DECAY_FLOOR env var
```

### 7.2 Per-episode-type half-lives

Different episode types decay at different rates, matching their real-world relevance horizon:

| episode_type | default half-life | rationale |
|---|---|---|
| `chat` | 48 hours | Recent conversation is relevant; week-old chat fades |
| `combat` | 72 hours | Combat memories linger a bit longer |
| `social` | 96 hours | Social bonds are slower to fade |
| `quest` | 168 hours (7 days) | Quest state is load-bearing across sessions |
| `discovery` | 720 hours (30 days) | Discovery facts are near-permanent |
| `goal` | 168 hours (7 days) | Active goals should persist across play sessions |
| `reflection` | 336 hours (14 days) | Reflections encode durable understanding |
| `observation` | 24 hours | Passive observations fade quickly |

These defaults are in `tot/memory/src/tot_memory/retrieval/decay.py` as a `HALF_LIVES_S: dict[str, float]` constant. All values are configurable via env vars at the format `MEMORY_HALF_LIFE_{TYPE_UPPER}` (e.g., `MEMORY_HALF_LIFE_CHAT=172800`).

### 7.3 `reflection` episodes as decay-resistant anchors

When the bot writes a `reflection` episode (a synthesized summary of a set of source episodes), the reflection carries the bot's durable understanding. The reflection's long half-life (14 days) means even if the source episodes have decayed to near-zero, the bot still "remembers" the gist. The source episode IDs are stored in `metadata.source_episode_ids` (§1.3) so a future compaction pass can identify and reclaim the originals.

## 8. Salience Scorer

### 8.1 Design choice: rule-based with discrete tiers

Salience scoring is rule-based with discrete tiers mapped to float values. An LLM-based scorer was considered and rejected for 1.0.0 because:

1. It would add a synchronous LLM call to the write path (forbidden per the architectural guardrails — must not add LLM latency to writes).
2. An async scorer breaks the "write and it's available" guarantee.
3. For a WoW bot, the event types and their salience are structurally predictable enough that rules work well.

The brain (agent-orchestration-architect's domain) may optionally include a `salience_hint` (0.0-1.0) in the `memory.write` call, overriding the server-side scorer. If `salience_hint` is present and in range, use it. This lets the LLM surface judgments the rule-based scorer can't make.

### 8.2 Salience tier table

```python
# tot/memory/src/tot_memory/salience/scorer.py
# SPDX-License-Identifier: GPL-2.0-or-later

from dataclasses import dataclass

SALIENCE_PIVOTAL     = 1.0   # First kill ever on a raid boss; player explicitly said "remember this"
SALIENCE_IMPORTANT   = 0.8   # Kill on a named dungeon boss; quest completion; goal achieved
SALIENCE_NOTABLE     = 0.6   # Named NPC interaction; group formed; player shared a goal
SALIENCE_NORMAL      = 0.45  # Typical social interaction; combat event (non-boss)
SALIENCE_FILLER      = 0.2   # Routine observation (player walked by); near-duplicate of recent episode
SALIENCE_TRIVIAL     = 0.05  # Transient system noise (heartbeat, tick-level non-events)

# Per-type default salience (before rule adjustments)
_TYPE_DEFAULT: dict[str, float] = {
    "chat":        SALIENCE_NORMAL,
    "combat":      SALIENCE_NORMAL,
    "social":      SALIENCE_NOTABLE,
    "quest":       SALIENCE_IMPORTANT,
    "discovery":   SALIENCE_NOTABLE,
    "goal":        SALIENCE_IMPORTANT,
    "reflection":  SALIENCE_IMPORTANT,
    "observation": SALIENCE_FILLER,
}
```

### 8.3 Scoring algorithm

```python
def score_salience(episode_type: str, metadata: dict, salience_hint: float | None = None) -> float:
    """Compute salience for an episode at write time.

    Args:
        episode_type: One of the valid episode_type values.
        metadata:     The parsed metadata dict for this episode.
        salience_hint: Optional override from the brain (0.0–1.0). If provided and valid, returned directly.
    """
    # Brain override takes precedence
    if salience_hint is not None and 0.0 <= salience_hint <= 1.0:
        return round(salience_hint, 3)

    base = _TYPE_DEFAULT.get(episode_type, SALIENCE_NORMAL)

    # Rule-based adjustments
    score = base

    # Combat: near-death is more salient than typical combat
    if episode_type == "combat":
        outcome = metadata.get("outcome", "")
        if outcome == "kill":
            score = max(score, SALIENCE_IMPORTANT)   # first/notable kill
        elif outcome == "near_death":
            score = max(score, SALIENCE_NOTABLE)
        elif outcome == "wipe":
            score = SALIENCE_IMPORTANT               # group wipes are memorable

    # Quest completion is more salient than accept
    if episode_type == "quest":
        event = metadata.get("event", "")
        if event == "complete":
            score = max(score, SALIENCE_IMPORTANT)
        elif event == "fail":
            score = max(score, SALIENCE_NOTABLE)

    # Goal completion
    if episode_type == "goal":
        event = metadata.get("event", "")
        if event in ("completed", "achieved"):
            score = SALIENCE_PIVOTAL            # goal completions should be remembered

    # Chat from a player (vs. NPC or self) is slightly more salient
    if episode_type == "chat" and metadata.get("source") == "player":
        score = max(score, SALIENCE_NOTABLE)

    return round(min(1.0, max(0.0, score)), 3)
```

### 8.4 Reinforcement via recall

Each time an episode is recalled (`memory.recall` or `memory.search`), `recall_count` is incremented. A future 1.1.0 enhancement can boost `salience_score` for frequently-recalled episodes (positive reinforcement). For 1.0.0, this is captured in the `recall_count` column but not yet used in scoring.

## 9. Per-Bot Namespacing

### 9.1 Decision: one SQLite file per bot_guid

Each bot has its own SQLite file at:

```
{MEMORY_DATA_DIR}/{bot_guid}/memory.sqlite
```

Where `MEMORY_DATA_DIR` defaults to `/opt/tot/data/memory` in production and `./data/memory` in dev. `bot_guid` is the low-32 integer GUID of the bot player character, formatted as a decimal string (e.g., `"1234567"`).

Example path: `/opt/tot/data/memory/1234567/memory.sqlite`

### 9.2 Why separate files vs shared file with bot_guid column

The plan description says per-bot file is the architecture. This is the right call for ToT:

- **Isolation:** A corrupted or bloated bot's DB cannot affect other bots. This matters for the `botActiveAlone` rotation (R5) — even if one bot has a runaway reflection loop writing thousands of episodes, the other bots' DBs are unaffected.
- **Operability:** `tot memory vacuum --bot-guid 1234567` operates on a single file. Operators can `cp` or inspect one bot's DB without touching others.
- **Simplicity:** No `WHERE bot_guid = ?` filter needed on every query — the filter is the file path itself.

Cross-bot queries (deferred to 1.1.0+) can be handled when needed via SQLite's `ATTACH DATABASE`.

### 9.3 Connection pool

One `sqlite3.Connection` per bot per request (open → use → close). WAL mode is set at connection open (§4 of connection.py in the plan). For the 1.0.0 scale (10 living bots × low request rate), a simple per-request open/close is fine. A connection pool (e.g., `threading.local` cache) is a 1.1.0 optimization.

### 9.4 `MEMORY_DATA_DIR` env var

```python
# tot/memory/src/tot_memory/config.py
MEMORY_DATA_DIR: Path = Path(os.environ.get("MEMORY_DATA_DIR", "./data/memory"))
```

The dir is created on first use (`mkdir(parents=True, exist_ok=True)`). The `tot-backup.sh` script (§6.5 of parent spec) must snapshot all files under `MEMORY_DATA_DIR/`.

**Purpose:** Like `memory.recall` but does NOT update `last_recalled_at` / `recall_count`. Use for meta-queries (e.g., "show me all memories about Alice") without changing the recall telemetry. Same request schema as `memory.recall`.

## 11. Migration Story

### 11.1 Decision: hand-rolled SQL migrations, not Alembic

Alembic is the right choice when the schema changes frequently and teams share DB ownership. For ToT's memory sidecar:

- The schema is owned by one subsystem (`tot/memory/`)
- Migrations are simple SQL (no Python logic needed for 1.0.0 migrations)
- Each migration file is executed once, tracked in `_meta_migrations`
- The migration runner is 40 lines of Python (already shown in the plan)
- No Alembic dependency = no alembic.ini, no env.py, no makefile generation target

If the schema grows complex enough to need Python-in-migration (data transforms during upgrade), add a `py:` prefix convention in migration filenames and extend the runner. For 1.0.0, this is not needed.

### 11.2 Migration file convention

```
tot/memory/src/tot_memory/db/migrations/
├── 000_meta.sql         ← placeholder (no-op); anchors directory for runner
├── 001_episodes.sql     ← episodes table + indexes
├── 002_entities.sql     ← entities + episode_entities + triggers
├── 003_embeddings_vec.sql  ← sqlite-vec virtual table
└── 004_episodes_fts.sql ← FTS5 virtual table + sync triggers
```

Naming convention: `{NNN}_{description}.sql`. `NNN` is a zero-padded 3-digit integer. Applied in ascending order. Never modify an applied migration — create a new one instead.

### 11.3 Runner behavior

```python
def run_migrations(conn: sqlite3.Connection) -> None:
    """Idempotent. Applies any migrations not yet in _meta_migrations."""
    _ensure_meta_table(conn)
    applied = {row[0] for row in conn.execute("SELECT version FROM _meta_migrations")}

    for version, filename, sql in _load_migrations():
        if version in applied:
            continue
        conn.executescript(sql)
        conn.execute(
            "INSERT INTO _meta_migrations (version, filename) VALUES (?, ?)",
            (version, filename)
        )
        conn.commit()
```

Runs at bot DB open time (in `open_bot_db`). The first open of a new bot's DB applies all 4 migrations atomically. Subsequent opens are fast (SELECT from `_meta_migrations` returns all 4 already applied, loop body is skipped).

### 11.4 Upgrade path for operators

When a new ToT version ships a new migration (e.g., `005_add_reflection_refs.sql`):

1. Operator runs `tot upgrade X.Y.Z` (§6.6 of parent spec).
2. The upgrade step stops the memory sidecar, starts the new image.
3. On first request per bot, `open_bot_db` runs migrations. New migration applies.
4. No manual intervention needed.

Forward-only migrations. No rollback DDL. If a migration must be reversed, a new migration does the inverse.
